# Running the Conformance Test Suite End to End

**Document ID:** EX-CONF-01

**Status:** Informative

**Version:** 0.1

**Last Updated:** 20 September 2026

---

# Purpose

`Governance/Conformance-Test-Suite.md` specifies how an implementation is tested and
`Governance/Test-Catalogue.md` binds each Statement to a Test. Neither could be run against
anything, because no exported model existed in this repository and the suite deliberately
prescribes no format. This directory is that missing input: one complete model, one Representation
Map describing it, one Conformance Statement, and the report the suite produces from them.

It is Informative. It defines nothing, adds no requirement, and makes no conformance claim. Its
only job is to let a reader run the suite in one command and see what a result looks like before
deciding whether to model their own systems this way.

---

# The Four Files

| File | What it is |
|---|---|
| `model.json` | One encoding of one model, the library lending example of `Adoption/Worked Example - Library Lending.md` carried down to the Models tier. The Specification prescribes no serialization (`Language/Serialization.md`, Independence); this is one, not the one. |
| `representation-map.md` | How each element of the OCOM vocabulary appears in that file. This is the artifact that makes a format-independent test possible, and the one an adopting organization writes for its own export instead of changing its systems to match a format OCOM does not prescribe. |
| `conformance-statement.md` | The five fields `Language/Conformance.md` lists, including the limitations this export knows about itself. |
| `report.md` | What the suite produced, regenerated by the command below. |

The report also carries a Reference Integrity section. No Statement binds it, so it is an observation rather than a Test outcome, but a model whose owner, Domain and Lifecycle references resolve to nothing passes its Presence Tests while meaning nothing, and a reader should see that before reading the verdicts.

---

# Running It

```text
python3 tools/conformance/validate.py \
  --model docs/Examples/Conformance/model.json \
  --map docs/Examples/Conformance/representation-map.md \
  --statement docs/Examples/Conformance/conformance-statement.md \
  --report docs/Examples/Conformance/report.md
```

Standard library only, no network, a few seconds.

# What the Result Says, and What It Does Not

At the commit that records this document: 187 mandatory Tests, 37 Pass, 0 Fail, 150 awaiting a
named reviewer or evidence this export does not carry. **Core Conformance is not established**,
and that is the correct answer rather than a disappointing one: Section 3 establishes it when
every mandatory Test is Pass or Review Pass, a model alone cannot produce a Review Pass, and this
example has no reviewer. An implementation plus a reviewer can.

The 150 are not a defect of the tool. 121 of them are Statements the Test Catalogue sends to
Review because no export can settle them, such as "Identity shall remain stable throughout the
Object's existence", which needs a history rather than a snapshot. The rest are prohibitions whose
evidence an export does not carry, and one Statement whose list items are not separated in its
source document, so the elements cannot be read out of it at all.

What the 37 do say is worth having, and no artifact in this repository said it before: every
Relationship in this model carries an identifier, a source, a target and a type; every Policy
carries an identifier, a name, a purpose, a scope and an effective date; every recorded State
change is one the Lifecycle permits; no Entity type is governed by two Domains; no governed record is without an owner; no
identity is used by two records. Those are machine verdicts on a real file, and a reader can break
the file and watch them turn to Fail, which is what thirty-two negative tests assert, including one that renames every field in the export and in the map together and requires every verdict to stay the same.

A compound Statement is never passed on part of itself. `A Lifecycle shall never: contain multiple
initial States; contain unreachable States; contain undefined Transitions; permit ambiguous State
progression` is checked on its first three parts and reported pending on the fourth, because no
export settles ambiguity. The report names which part is missing rather than rounding up.

# How an Adopter Would Use This

Write a Representation Map for an export you already have, run the command against it, and read
the failures. The first run of this example failed seventeen Tests, and the three kinds of failure
it produced are the three an adopter meets: elements the model genuinely lacked, elements the
model had under a name the map had not bound, and Statements the engine could not read. The first
kind is work on the model, the second is work on the map, and the third belongs back here as a
defect report.
